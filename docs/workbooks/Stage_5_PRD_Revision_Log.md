## 3 Section three: assumptions that turned out to be wrong

<!-- docx-table: 4 -->
| Assumption from version one | Did it hold? | What you found instead | What you changed because of it |
|-----------------------------|--------------|------------------------|--------------------------------|
| The pack's threshold of 0.80 is a reasonable starting point for routing. | No | At 0.80 almost nothing auto-responds on this classifier's confidence distribution (FCR proxy 5.8%); 0.35 gives FCR proxy 74.2% with escalation 25.8%. | Measured and froze 0.35; freeze recorded in `threshold-freeze.md` with `threshold_applied` on every decision (C-02, C-03). |
| A rules-plus-GLiNER zero-shot approach would classify intent adequately. | No (abandoned by decision, not by experiment) | The labelled development set allows a supervised classifier with the already-pinned scikit-learn stack, and it reached about 98.8% label accuracy on validation. | Dropped GLiNER (findings D5); no LLM labelling (C-01). |
| The development tickets are representative of the grader's hidden set. | Partly: cannot be fully tested | The validation file behaved close to development after the fixes (recorded first-contact resolution 82.5% on validation, 77% on a 100-ticket development sample before the fairness fix, 65% on validation before it), but the hidden set cannot be inspected. | Kept the harness path-driven, never tuned on validation, and added label-free policy rules (C-05). |
| Free-tier model limits allow a full live-generation evaluation if responses are cached. | No | The batch generation-enabled run was rate-limited and was not recorded; the human review used passage-grounded drafts written by the reviewer. | Added timeout, backoff and escalation (C-09); blocked business-metric claims on runs without generation (C-10); stated the limitation in the human-evaluation appendix. |
| Fairness can be judged by comparing raw auto-respond rates across segments. | No | The tier gap of about 35 points was mostly the uneven spread of policy-restricted tickets, not worse answers. | Switched to resolution quality on tickets that should be auto-answered (C-07); gap 0.0 points on validation after the fixes. |
| The embedding model and the index are available and consistent at run time. | No (first run) | The embedder fell back to an untrained model, and retrieval silently returned nothing; all 80 tickets escalated. | Dimension check and index health (C-11). |
| Success is judged against the success table, not the client wish-list row. | Yes | No evidence against it; the Evaluation Framework definitions are in the success table (findings D1). | No change; the wish-list figures are reported as context. |

## 4 Section four: what you decided not to change

<!-- docx-table: 5 -->
| What looked wrong | Why you left it | What it would have cost to change | Revisit when? |
|-------------------|-----------------|-----------------------------------|---------------|
| Escalating about one ticket in six (17.5% on validation, after the fairness fix) looked like missed auto-responses. | Escalation is correct for policy-restricted tickets (14 in the validation file) and for tickets with no documentation answer (17.4% and 28.6% of development tickets, Stage 1 §2.8, §2.12). Counter-metric: do not answer ungroundable tickets to improve a number. | Answering more would raise hallucination risk and break Marcus's "silence over error". | If the live-generation review shows hallucination well under 5% on more automation. |
| A single generation prompt with no examples. | Examples taken from easy cases teach the model that every case is easy; the prompt library check (Stage 3) found the format instruction, not the lack of examples, to be the gap. | Time to build and evaluate variants, which is also on the drop list. | After the output-format instruction is fixed and live generation can be measured. |
| Regex-based private-data and injection checks rather than a model-based filter. | Deterministic, explainable and cheap; a model-based filter would use the free-tier quota. | A second model call per auto reply plus its own evaluation. | If review finds missed private data or injection phrasing. |
| SQLite for the decision log instead of a server database. | Sufficient for a single-process evaluation; an export is shipped with the submission. | Migration, deployment and connection handling with no marked benefit in the cloudserve. | If more than one process writes decisions in a deployment. |
| Embedding-only retrieval with no hybrid search or reranking. | Citation validity is enforced in code, and relevance is controlled by a measured floor; hybrid search is on the drop list. | About two hours plus an evaluation. | If citation accuracy in the live review falls below 95%. |

## 5 Section five: the reflection

<!-- docx-table: 6 -->
| Question | Your answer |
|----------|-------------|
| What did you most misunderstand about the problem when you wrote version one? | Version one treated the pack's illustrative numbers as settled and treated fairness as a matter of counting automated replies per group. The build showed that the classifier's confidence sits far below 0.80, so the pack default would have escalated nearly everything, and that the tier gap in automated replies came mostly from how policy-restricted tickets are spread across tiers rather than from worse answers. I also wrote the product as a chain of components, when the discovery evidence said the value is in routing correctly and giving agents context on every escalation. |
| Which piece of discovery work would have caught it earlier? | A threshold sweep on the development data before writing the PRD, and a policy-restricted share by tier in the discovery aggregates (Stage 1 gave the overall 17.4% but not the split). Running the unattended harness end to end with generation stubbed in the first days of week two, rather than on the Friday gate, would also have exposed the embedder fault earlier. |
| What would you do differently if you started this project again on Monday? | Run the threshold sweep and the full harness on the validation file as soon as retrieval and the classifier exist; add a health check on the embedding dimension from the start; settle the output-format contract of the generation prompt with one live call before writing guardrails; and start a live generation batch early so that free-tier limits do not leave the answer-quality evidence simulated. |
| What is still uncertain, and what would you need to resolve it? | Quality of real model output is not measured: hallucination, citation accuracy and satisfaction were reviewed on passage-grounded drafts, and the prompt's output-format instruction is not currently sent with the messages (Stage 3 weakness 1). Resolving it needs a live generation run inside the free-tier quota and a human review of the real drafts. Also uncertain: behaviour on the hidden set, Marcus's definition of first-response time, and the disclosure wording for automated replies. |
